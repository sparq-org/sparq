# SLSA controls → status → evidence (sparq)

**Framework:** SLSA — Supply-chain Levels for Software Artifacts (v1.0, Build track + the
Source/Provenance/Verification dimensions). <https://slsa.dev/spec/v1.0/>

**Honest headline level:** sparq's **release artifacts** (the `release.yml` packaged archives
*and* the ghcr.io container image) meet **SLSA Build Level 2** — they carry signed,
authenticated provenance generated by a hosted build platform (GitHub Actions) via
`actions/attest-build-provenance` (Sigstore) and buildkit `provenance: mode=max`. sparq does
**not** claim **Build Level 3**. The in-band provenance every artifact carries is generated *inside
the same job* that runs the build, so a compromised build step could in principle influence the
provenance it is later attested under — the L2 ceiling. Isolated trusted-builder lanes that lift
that ceiling now exist for **every** `release.yml`/`dist.yml` artifact (sq-toze.25 → #4570 → #4635,
the last covering the ghcr image via the generator's container builder), but **not one of them has
executed** — `release.yml` is tag/dispatch-triggered and `dist.yml` dispatch-only — so they are
audit-ready, not verified, and the published level stays **L2**. See SL-B3-b.

> **Scope note (library vs service).** SLSA scores a *build → artifact* pipeline. sparq ships
> several artifacts: the `sparq-cli` binaries (release.yml + dist.yml), the `sparq-server`
> container (release.yml), the crates.io source crates, and the npm/PyPI bindings. This table
> scores the **binary + container** pipeline (where provenance attestation lives). The crates.io
> publish path is currently a manual `cargo publish` and is scored as a gap (SL-B2-e). The source
> track (version control, two-person review, retention) is scored under "Source / Build-platform
> integrity" below.

> **Honesty contract.** Each row is labelled **implemented & verified** (a control with passing
> CI/file evidence), **audit-ready** (control + doc in place but the *level certificate* needs the
> external evidence SLSA defines — e.g. a third-party provenance verifier, an isolated builder we
> do not operate), or **gap** (not met → `gap-register.md` + a `bd` bead). No SLSA *level* is
> claimed beyond what signed provenance backs. The number we publish is **Build L2**, never L3.

Legend — Status: **IV** implemented & verified · **AR** audit-ready · **GAP**. Evidence paths are
repo-relative.

| ID | SLSA requirement | Status | Evidence | Owner |
|---|---|---|---|---|

| SL-B2-d | **No unattested binary in the release path** | **IV** | **Closed (GX-9 / sq-toze.23).** `dist.yml#build` now mirrors `release.yml#package`: `permissions: id-token: write` + `attestations: write`, `cargo auditable build --release --locked`, and `actions/attest-build-provenance@a2bbfa2… # v4.1.0` over the per-tier binary (`subject-path: dist/sparq-cli-${{ matrix.tier }}${{ matrix.ext }}`). Both the tag-time and `workflow_dispatch` dist builds are covered. | release eng |
| SL-B2-e | **Published-package provenance** — the artifact as consumers fetch it carries provenance (crates.io / npm / PyPI) | **IV (npm) / PARTIAL (crates.io) / CI-WIRED, maintainer-config-pending (PyPI)** | **GX-10 / sq-toze.24 addressed for npm; crates.io-native sub-gap stays OPEN (external); PyPI PEP-740 lane wired in CI, awaiting a one-time PyPI Trusted-Publisher registration (sq-toze.37).** Added a publish workflow [`.github/workflows/publish.yml`](../../.github/workflows/publish.yml) — `release: published` + maintainer `workflow_dispatch`. **npm (`#npm`):** `npm publish --provenance --access public` runs in this GitHub Actions OIDC context (`permissions: id-token: write`, `setup-node` `registry-url`); npm's registry records a Sigstore-signed in-toto SLSA build-provenance statement bound to the run, and a post-publish step (`npm view … dist.attestations`) fails the job if the published version lacks a recorded attestation. This gives an **out-of-band** attestation a consumer can `gh attestation verify <file>.crate --repo sparq-org/sparq` against the downloaded crate — it does NOT place provenance on crates.io itself. The crates.io-native link remains an OPEN external sub-gap of GX-10. **PyPI (`#pypi-build`/`#pypi-sdist`/`#pypi-publish`, sq-toze.37):** the `sparq-rdf` wheels (maturin matrix: manylinux x86_64/aarch64, macOS arm64/x64, Windows x64) + sdist are uploaded via PyPI **Trusted Publishing** with native **PEP-740 attestations** — `pypa/gh-action-pypi-publish` with `attestations: true` runs in this OIDC context (`id-token: write`) so PyPI records an in-toto/Sigstore-signed provenance statement per file and shows a "Provenance" panel on the release-files page (verify: `pypi-attestations verify` / `gh attestation verify`). This is the PyPI-native equivalent of npm `--provenance` — the **strongest** of the three lanes. The CI is fully wired; the ONE remaining item is **maintainer-side, not repo-side**: a Trusted Publisher must be registered on the `sparq-rdf` PyPI project (owner `sparq-org`, repo `sparq`, workflow `publish.yml`, env `pypi`); until then the OIDC token mint fails by design (no static token is stored). → **GX-10 / beads sq-toze.24 (npm/crates) + sq-toze.37 (PyPI)**. | release eng |

**Build L2 verdict: MET (implemented & verified) for the `release.yml` archives + the ghcr.io
container + the `dist.yml` tiered binaries (SL-B2-d closed, GX-9 / sq-toze.23) + the `@sparq-org/sparq`
npm package (SL-B2-e, `publish.yml#npm` — native Sigstore provenance, GX-10 / sq-toze.24).** The
crates.io published `.crate` artifacts now carry an **out-of-band** SLSA attestation
(`publish.yml#crates`, `gh attestation verify`), but crates.io has **no native provenance link**
upstream — that sub-gap is recorded as OPEN/external under GX-10. The PyPI `sparq-rdf` lane
(`publish.yml#pypi-build`/`#pypi-sdist`/`#pypi-publish`, sq-toze.37) is **wired** to upload via
Trusted Publishing with native **PEP-740 attestations** (`attestations: true`, OIDC) — once a
maintainer registers the Trusted Publisher on the PyPI project, PyPI emits a native provenance

fails to mint a token by design; the CI is complete, the account config is the only open item.

## Build track — Level 3 (hardened, isolated build; non-falsifiable provenance)

| ID | SLSA requirement | Status | Evidence | Owner |
|---|---|---|---|---|
| SL-B3-a | **Isolated builds** — the build runs in an ephemeral, isolated environment; build steps cannot influence one another across runs | **AR (partial)** | GitHub-hosted runners are ephemeral per job (clean VM, destroyed after). This satisfies the *ephemerality* aspect but not the full L3 *builder isolation* model. | release eng |
| SL-B3-b | **Provenance unforgeable by the build process** — provenance is generated by a trusted control plane the build steps cannot tamper with (e.g. the `slsa-github-generator` trusted reusable workflow, where signing happens in a separate job the user build cannot reach) | **AR (every `release.yml`/`dist.yml` artifact, container included — WIRED, unexercised)** | **Four isolated trusted-builder lanes, all calling a `slsa-framework/slsa-github-generator` reusable workflow at `@v2.1.0` as a bare `uses:` in their own job.** Three call the **generic** generator (`generator_generic_slsa3.yml`), whose single boundary input is `base64-subjects` — a file-digest list: (1) `release.yml#provenance` — the CLI/server **archives** (sq-toze.25), subjects threaded from `build-matrix.yml`'s `hashes` output; (2) `release.yml#provenance-artifacts` — the **GUI bundles, SBOM/VEX and served-surface conformance report** (#4570), subjects threaded from the `artifact-subjects` collector; (3) `dist.yml#provenance` — the **tiered bare binaries** (#4570), subjects threaded from `build-matrix.yml`'s `binary-hashes` output. The fourth calls the **container** generator: (4) `release.yml#provenance-container` — the **ghcr.io `sparq-server` image** (#4635). A registry image is not a file, so that lane takes `image` + `digest` instead of `base64-subjects` — the OCI index digest the `docker` job's push step reported, threaded as a job output (never a tag, which is mutable) — and the generator attaches the attestation to the image in ghcr.io rather than emitting a bundle. Each builder job mints its own OIDC identity and runs no step of ours (no `steps:`/`run:`). Each digest-collecting job builds nothing and holds no signing identity (`contents: read`, no `id-token`) and validates the blob fail-closed (malformed record, empty set, or a missing lane → job reds). No builder job holds `contents: write`; the three generic lanes set `upload-assets: false` (the `release` job attaches both bundles, so they land in `SHA256SUMS`, and `release` **`needs:` both**, so no Release is cut without them), while the container lane holds `packages: write` because it *is* the uploader. All four shapes pinned on every PR by `scripts/tests/test_release_slsa_l3_provenance.py` (stdlib, mutation-proved). **Verification of the FILE bundles is automated, not a manual instruction** (#4571): `release.yml`'s `verify-provenance` job — `needs: release`, so it runs once the Release exists — calls `release-verify.yml`, which runs `scripts/verify-release-provenance.sh`, which re-downloads the published assets and reds unless both bundles are attached AND listed in `SHA256SUMS`, `SHA256SUMS` matches the published bytes, and `slsa-verifier verify-artifact … --source-uri github.com/sparq-org/sparq` accepts **every** asset against one of the two bundles (an asset covered by neither, an empty asset set, or a bundle covering nothing it published all fail the run — the vacuous-pass class). Its `provenance-verification.log` is the artifact this row will cite when it moves to IV; the script's own fail-closed branches are mutation-proved on every PR by `scripts/tests/test_verify_release_provenance.sh`. That sweep does **not** cover the container attestation, which lives in the registry, not the Release — verify it by hand: `slsa-verifier verify-image ghcr.io/sparq-org/sparq-server@<digest> --source-uri github.com/sparq-org/sparq` (ghcr.io needs `GH_TOKEN` exported). **AR not IV, on three counts:** (i) `release.yml` is tag/dispatch-triggered and `dist.yml` is dispatch-only, so **no lane has yet executed** — first exercised on the next `v*` tag / dispatch; (ii) both generators *attest*, they do not *build* — they sign digests our build jobs reported, delivering the *unforgeable-provenance* half of SL-B3-b, not a hardened build; (iii) the container lane cannot be fail-closed the way the file lanes are — an image has no digest until it is pushed, so publication necessarily precedes attestation, and a failed `provenance-container` reds the run over an image already in ghcr.io. The buildkit in-band attestation (`provenance: mode=max` + `sbom: true`, read by `cosign verify-attestation`) is deliberately retained alongside the isolated lane: different predicate, different attachment, not interchangeable. → **GX-11 / beads sq-toze.25 + #4570 + #4635 (coverage residual CLOSED; still open on `unexercised`)**. | release eng |
| SL-B3-c | **Parameterless / fully-described builds** — no build parameters that change the artifact without appearing in provenance | **AR** | Builds are pinned: `--locked` (Cargo.lock), SHA-pinned base image (`Dockerfile` `rust:1.88-slim-bookworm@sha256:…` + `gcr.io/distroless/cc-debian12:nonroot@sha256:…`), SHA-pinned actions. `RUSTFLAGS`/`target-cpu` per tier are in the workflow source (in provenance via the recorded entry-point) but the *value* is not separately surfaced in the predicate. Documented, not independently verified. | release eng |

**Build L3 verdict: NOT MET — and the remaining blocker is now evidence, not coverage.**
sq-toze.25 wired the isolated trusted builder for the **release archives**; #4570 extended it to the
**GUI bundles, SBOM/VEX, served-surface conformance report and `dist.yml`'s tiered binaries**; #4635
completed the sweep with the **ghcr.io container image**, via the generator's separate container
builder (SL-B3-b above). Coverage is no longer a gap. Three things still stop this from being an L3
*claim*, and the third is the one most easily glossed over:

1. **Unexercised.** `release.yml` runs only on `v*` tags / `workflow_dispatch` and `dist.yml` only on
   `workflow_dispatch`, so **no** trusted-builder job has ever executed. Wiring is not evidence. The
   claim stays **L2** until a real tag produces verifiable `.intoto.jsonl` bundles (verify:
   `slsa-verifier verify-artifact <file> --provenance-path <bundle> --source-uri
   github.com/sparq-org/sparq`, where `<bundle>` is `sparq-cli-<version>.intoto.jsonl` for an archive and
   `sparq-artifacts-<version>.intoto.jsonl` for a GUI bundle / SBOM / VEX / conformance report).
   What #4571 changed is *how that evidence gets produced*, not whether it exists yet:
   `release.yml`'s `verify-provenance` job now runs exactly those verifications automatically once
   the Release is cut — it calls `release-verify.yml`, which runs
   `scripts/verify-release-provenance.sh` — fail-closed and over **every** published asset, so
   the first `v*` tag either produces a citable green run or reds loudly — the flip no longer depends
   on someone remembering to verify by hand. Scope: the two RELEASE bundles only — `dist.yml`'s
   `sparq-dist.intoto.jsonl` is a run artifact, not a Release asset, and the container attestation
   lives in ghcr.io rather than on the Release, so nothing automatically verifies either. Verify the
   image by hand from the run's pushed digest: `slsa-verifier verify-image
   ghcr.io/sparq-org/sparq-server@<digest> --source-uri github.com/sparq-org/sparq` (ghcr.io needs
   `GH_TOKEN` exported). Until such a run exists,
   this item is **NOT discharged**.
2. **The container lane cannot be fail-closed** (#4635). The file lanes are: `release` `needs:` both
   provenance jobs, so an unprovenanced archive is never published. An image has no digest to attest
   until it has been pushed, so publication necessarily *precedes* attestation — a failed
   `provenance-container` reds the run over an image already in ghcr.io, to be dealt with by fixing
   forward. This is a permanent asymmetry of the registry model, not a wiring defect, and it means
   "the ghcr image carries isolated provenance" is a weaker statement than the same sentence about an
   archive. Automating the `verify-image` check alongside `verify-provenance` would narrow it; that
   is **not** wired.
3. **The generators attest, they do not build.** Both `generator_generic_slsa3.yml` and
   `generator_container_slsa3.yml` take digests our own jobs computed and sign a statement about them
   in isolation. That is exactly the SL-B3-b property — provenance the build process cannot forge —
   but it is **not** the stronger "the artifact was produced inside the trusted builder" property that
   a language-specific builder (e.g. the Go builder) gives. A compromised build step still yields
   honest provenance *about a compromised artifact*. Anyone reading the generator's marketing as "we
   are SLSA 3" is overclaiming; what sparq gets is unforgeable provenance, not a hardened build.
   Widening the *coverage* (#4570, #4635) does not touch this: six artifacts now get the same bounded
   property the archives got, and the bound is unchanged.

SL-B3-a (isolated builds) is likewise unchanged: hosted runners give ephemerality, not the full L3
builder-isolation model. **Do not publish an L3 claim for any artifact until all three items above
are discharged** — the defensible claim today remains Build L2, exactly as before this change.

## Source / Build-platform integrity (the inputs SLSA's provenance must trace to)

These are not numbered "Build levels" but are the source-track + verification controls SLSA's
provenance binds to. sparq's posture here is **strong** and is what makes the L2 provenance
meaningful.

| ID | Control | Status | Evidence | Owner |
|---|---|---|---|---|
| SL-S-a | **Version-controlled source** — every build input traces to an immutable VCS revision | **IV** | All builds run from `actions/checkout` at the tagged commit; tags are immutable on a protected branch. | release eng |
| SL-S-b | **Two-person review** — changes to the source require review by someone other than the author | **AR** | `CODEOWNERS` (`@jeswr` owns all + high-risk paths `sparq-zk*`/`sparq-mpc`/`sparq-core`/`sparq-server`/`.github/`/`deny.toml`/`SECURITY.md`); `docs/branch-protection.md` records the live solo-maintainer ruleset: zero required approving reviews, no required code-owner review, no stale-review dismissal, linear history, and blocked force-push. The repository-administrator role has an always-on bypass; the automated landing path does not use it. **AR not IV** because the ruleset is configured out-of-repo on GitHub (can't be a tracked file) — the doc is the reproducible record; an auditor confirms the live setting. A single-maintainer project does not satisfy "different person" review — recorded honestly. | maintainer |
| SL-S-c | **Protected branch / no force-push / linear history** | **AR** | `docs/branch-protection.md` ("History and push rules": require linear history, block force-push, block branch deletion). The repository-administrator role can always bypass these rules; the normal automated landing path remains constrained by merge-queue admission. Out-of-repo setting → audit-ready. | maintainer |
| SL-S-d | **Single required merge gate** | **IV** | `.github/workflows/ci-summary.yml` (`ci-summary / gate`) aggregates every check-run and is the sole required status check (`docs/branch-protection.md`). | platform |
| SL-S-e | **Pinned, locked dependencies** — build materials are immutable | **IV** | `Cargo.lock` checked in + every build uses `--locked` (`release.yml`, `dist.yml`, `Dockerfile`); SHA-pinned base images + SHA-pinned third-party actions across all workflows (`# vX.Y.Z` Dependabot trailer convention). | platform |
| SL-S-f | **Dependency-source restriction** — only trusted package sources | **IV** | `deny.toml [sources]` `unknown-registry = "deny"`, `unknown-git = "deny"` (crates.io only); GATING via `.github/workflows/supply-chain.yml#audit` (`cargo deny check … sources`). A new unaudited dep fails the gate. | platform |

| SL-S-i | **Restricted, least-privilege build tokens** | **IV** | Top-level `permissions: contents: read` in every workflow; jobs opt into the minimum (`id-token: write`/`attestations: write` only where attesting, `packages: write` only on the docker push job). `persist-credentials: false` on the Scorecard checkout. | platform |
| SL-S-j | **Machine-discoverable vuln-disclosure channel** (provenance consumers need a report path) | **IV** | `.well-known/security.txt` (RFC 9116) + `SECURITY.md` (GHSA + email, response targets, the ZK-not-sound caveat). | maintainer |
