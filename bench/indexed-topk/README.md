# Indexed top-k local diagnostic

[GPT-6 Astra] Bench-only source for the PR5983 recovery (issue6465). This follows the standalone `bench/alloc-track` and separate counting/timing build conventions. It changes no production feature, dependency, gate or baseline. Measurements are local diagnostics, never canonical performance claims.

Build from this directory with `cargo build --release --locked --offline`; add `--features count-alloc` for the separate allocation binary. Use two build jobs and a task-local `CARGO_TARGET_DIR`. The harness fixes Rayon to one thread. `selftest` calibrates allocation, zeroed allocation, reallocation and deallocation accounting in the counting build.

The binary accepts `MODE CASE N K WARMUP REPS EXPECTED_PATH`. Modes are `verify` and `measure`; cases are `base`, `overlay`, `drained`, `drained-overlay`, `ties`, `ties-overlay`. Run verification in its own process: it checks an independent Rust total-order oracle and the existing BGP trace outside timing. Indexed engagement is currently inferred from absence of that trace; explicit optimizer tracing remains separate pre-admission work.

Compare three source configurations using byte-identical harness, lockfile, features, profile and thread count: exact reviewed candidate; that candidate with only indexed admission disabled; exact main base. Preserve each source diff/hash and final binary hash. Copy each built binary before reusing the private build target. Never switch the shared checkout. The complete local runner and raw data are task artifacts, not canonical bench uploads.

Use favorable small and larger limits for both base and overlay graphs, plus drained and oversized-tie cases on both storage forms. All fixtures contain the priority seed plus six probe predicates. The overlay deletes every fifth subject's complete seven-triple star and retains its original snapshot. Drained fixtures keep the pending cardinality just above the upfront half-extent decline; ties deliberately exceed the actual post-deletion group cap. Dimensions and pending tombstones are asserted and emitted. Query results are compared to a generated total order on priority and unique sequence.

Timing covers the full `sparq_engine::query` call, including parse, evaluation and result construction; result checking, formatting and destruction are outside the window. The timing build uses the unwrapped System allocator. Allocation builds do not report perturbed latency. Counts cover successful allocation/zero-allocation calls and successful reallocations separately; requested bytes include the full new size for each reallocation. Peak live delta counts requested layout sizes above the window's live baseline, including retained caches; it excludes allocator metadata, stack, memory maps and transient storage internal to `System::realloc`.

RSS is the OS cumulative process high-water mark, recorded after fixture construction and before/after measured queries. Setup can dominate it, so a zero increase cannot establish zero query memory. Allocation-window peaks provide a separate query-specific requested-heap estimate. Start each case/mode in a fresh process, retain setup and query observations separately, and report this limitation rather than relabeling cumulative RSS as a resettable query peak.
